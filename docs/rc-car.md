# RC car setup and Traxxas ESC calibration

Select an RCPv1 firmware build and vehicle profile for the actual board and harness. Keep the profile header, built UF2, manifest and chosen Pico serial together in deployment records. Both Waveshare RP2040-Zero and RP2350-Zero can be built. The firmware repository's example profile is a starting point for a bench build. Physically qualify it before enabling a vehicle. Use physical BOOTSEL with actuator power isolated and verify the running device and profile afterward.

Build and install rc_car_interface on the ROS 2 Jazzy host. Add its namespaced vehicle.launch.py to the selected vehicle composition, passing device_id, profile_id and build_id from that selection. Use a distinct namespace per car. For an independent launch on a prepared host, pass those three arguments and namespace to ros2 launch rc_car_interface vehicle.launch.py. The current RGB-D demo remains an independent perception composition. Runtime can supervise the vehicle process using the existing launch and status capabilities.

## Direct Pico commands

~~~sh
lucid_conduct pico list --json
lucid_conduct pico rc-car status
lucid_conduct pico rc-car watch --duration 10
lucid_conduct pico rc-car doctor
lucid_conduct pico rc-car mode hold
lucid_conduct pico rc-car mode manual
~~~

List uses USB metadata. Status, watch, and the link check in doctor take an exclusive RCPv1 session. If the interface owns the port, read live status through runtime. On a managed site, mode changes require stopped management and resolved workload ownership. They use the private device, profile and build pins. With no selected deployment, pass `--standalone --client /absolute/path/to/rc_car_ctl` and the exact `--device-id`, `--profile-id` and `--build-id` for mode changes.

Manual releases Hold and reports the observed mode. Neutral with an RC-related reason means the Pico is waiting for the receiver and a fresh in-band throttle sample. Hold inhibits drive and steering, and pan remains independent. A lost command result is uncertain. Inspect status before retrying. The staged PWM fields report what firmware programmed.

## Select and build RCPv1 firmware

Keep the default RGB-D composition unchanged. In a separate trusted composition, select `firmware.rc_car` with a source URL and full commit, component path, board and a definition-relative profile header. The header bytes are included in the installed definitions. After installing that selection, build the bundle:

~~~sh
lucid_conduct info mcu rc-car
lucid_conduct build mcu rc-car
~~~

The firmware entry and optional vehicle unit look like this. Add them to the existing mappings in the selected composition and replace each commit placeholder with the exact revision.

~~~yaml
firmware:
  rc_car:
    source:
      url: https://github.com/pbeuchat43/rc_car_firmware.git
      commit: "<full firmware commit>"
    path: "."
    board: waveshare_rp2040_zero
    profile: profiles/vehicle.hpp
units:
  vehicle:
    launcher: rc_car_interface
    source:
      url: https://github.com/pbeuchat43/rc_car_interface.git
      commit: "<full interface commit>"
~~~

To install the interface and expose it to runtime, add `units.vehicle` with `launcher: rc_car_interface` and a `source` mapping containing the interface URL and an exact RCPv1-compatible commit from 0.3.0 onward. In the private site set `hardware.rc_car` with the application device ID and the profile and build IDs from the RCPv1 manifest. The earlier RC1 development firmware needs its matching host release. Bootstrap this deployment with the pinned runtime 0.1.0.dev27, which supports recording and the bounded strings generated by Jazzy. Provision the selected release with that composition. The vehicle and recording units remain independent and are started explicitly.

Use the firmware manifest from the selected build. Stop the selected site's management and workloads, isolate actuator power, and put the board into physical BOOTSEL. Use `pico list` to verify its USB port. Supply the Pico's application device ID, which for RP2040 is its flash ID and for RP2350 is its chip ID. It can differ from the ROM USB serial.

~~~sh
lucid_conduct flash mcu rc-car --device-id EXACT_DEVICE_ID \
  --manifest /absolute/build/rc_car_firmware.manifest.json --actuators-isolated
~~~

The command verifies and records a rollback copy, verifies the new bytes, and checks the RCPv1 application at the same USB port after reboot. A flash report distinguishes byte verification from application verification. The operator needs read/write permission on the BOOTSEL USB device and the application tty. The command runs without sudo.

## Observe and request modes through runtime

The optional vehicle composition declares `vehicle_status` and `vehicle_mode`. Use the declared capabilities with the interface running.

~~~sh
lucid_conduct runtime start vehicle
lucid_conduct runtime ros watch --topic vehicle_status
~~~

For `lucid_conduct runtime ros call vehicle_mode --expected-run RUN_ID --arguments JSON`, use the current run ID and a fresh observation whose provider `fresh` field is true. Supply `session` and `generation` from that observation, the current system time as `stamp_ns` at submission, numeric `mode` (Manual 1, Auto 2, Hold 3), and numeric `drive_choice` and `steer_choice` (default 0, Host 1, RC 2, Sum 3). The JSON representation uses decimal strings for `stamp_ns` and `generation`. Requests expire at the interface after 200 ms. Generate the timestamp programmatically when calling. This generic capability does not supply a stamp or session from the browser form.

## Calibrate a Traxxas ESC

For XL-5 or VXL-3s ESC setup, use the specific manual for the unit installed. Stop runtime management and all supervised workloads, and stop any standalone vehicle interface. Confirm propulsion isolation as required by the manual. The wizard reserves deployment and runtime maintenance and then opens the selected Pico exclusively. It compares the configured neutral with the actual programmed neutral before entering Maintenance mode.

~~~sh
lucid_conduct calibrate traxxas esc --site /path/to/site.json \
  --esc xl-5 --device-id YOUR_PICO_SERIAL --profile-id YOUR_PROFILE_ID \
  --build-id YOUR_BUILD_ID --maintenance-client /absolute/path/to/rc_car_maintenance_link
~~~

Specify --neutral-us, --forward-us and --reverse-us to match the selected profile and calibration endpoints. Defaults are 1500, 2000 and 1000 µs. Follow the model's prompts. The command records operator-confirmed ESC acceptance under the site's private data root. The Pico remains in Hold on completion, abort or link loss. Confirm actual ESC neutral and PWM before restoring propulsion, then explicitly release Hold through the vehicle interface.
